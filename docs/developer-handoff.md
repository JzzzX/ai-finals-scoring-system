# AI先锋赛决赛评分系统 · 开发交接

交接日期：2026-09-18。当前版本可本地运行，供开发同事查看、接入飞书 OAuth 和部署。参赛材料与正式评委名单尚待确认，后续再完善对应页面和权限。

## 1. 接手后先做什么

1. 从 [Gitea](http://192.168.180.119:3000/ai-itbp/ai-finals-scoring-system) 或 [GitHub](https://github.com/JzzzX/ai-finals-scoring-system) 拉取源码，两端维护同一项目。
2. 按 [README](../README.md) 安装依赖、初始化管理员、构建并启动。要求 Node.js 24+，本机验证版本为 26.6.0。
3. 管理员登录后，在“成员与权限”创建初版查看评委。分别查看 `/admin/results`、`/admin/users`、`/admin/settings` 与 `/score`。
4. 在独立联调数据库完成开赛、提交、改分、结束、导出流程，然后接入飞书登录和部署环境。
5. 正式名单与材料确认后，完成内容更新、角色配置和比赛环境验收，再开始正式评分。

`http://127.0.0.1:3001` 只指向访问者自己的电脑，不是供同事远程访问的部署地址。当前没有生产域名或已部署服务交付。

## 2. 初版账号与当前数据

| 身份 | 账号 | 密码 | 用途 |
| --- | --- | --- | --- |
| 管理员 | `admin` | `admin12345678` | 查看成绩、配置成员权限、控制赛事 |
| 评委 | `judge` | `judge12345678` | 查看评分页及本人记录 |

这些账密已公开，仅供初版联调。当前维护者本机数据库已配置两账号；新环境需按 README 初始化，代码不会自动生成它们。管理员不自带评委资格，评委不能访问后台，已验证后台接口返回 403。

截至交接时，本机为 12 支真实队伍、44 条成员记录、12 张照片、0 份评分，赛事状态 `draft`。`judge` 是查看用账号，正式评委名单未确认。数据库、登录会话和备份不随 Git 同步。

联调请使用单独的数据库，例如在联调环境 `.env` 中设置 `DB_PATH=./data/review.sqlite`，再初始化管理员和评委。切换数据库前停止旧进程，修改后重新启动；确认界面和数据对应新库后再开始评分。正式库应保持未开赛、无联调成绩。不要通过删除评分记录临时拼出正式库。

## 3. 已完成的功能与规则

- 评委端：电脑与手机布局、队伍资料、六项参考标准、滑块与数字输入、选填评语、本人历史评分、草稿恢复与冲突提示。
- 管理员端：队伍 × 评委成绩矩阵、均分与排名、缺评名单、CSV 明细与汇总、成员停用与角色设置、改分审计、开始与结束评分。
- 每队一个综合分，0—10 分、间隔 0.5；六项维度只作参考，不重复加权。0 分有效，未评分不参与平均。均分显示两位小数，按未舍入结果排名，完全同分并列。
- 截止前可修改本人评分；版本号、幂等请求和事务避免重复写入及双设备覆盖。截止后服务端拒绝提交，重新开放需管理员填写原因。
- 开赛固定评委名单，后续新增账号不自动纳入；重新开放也不重建名单。角色变更保留已有成绩，管理员不能代评。

目前不包含飞书 OAuth、生产部署、参赛材料上传或选手账号。后续材料入口需要新增产品流程和权限，不能把当前评委角色直接当作选手角色使用。

## 4. 飞书 OAuth 接入任务

详细接口与认证边界见 [飞书与部署接入说明](feishu-handoff.md)。开发同事需先确定飞书应用、允许登录的租户、访问域名和回调地址，并由对应应用管理员配置。

建议实施顺序：

1. 在 `server/identity.ts` 附近新增飞书身份适配器及独立登录、回调路由。当前接口只支持本地账号密码，不能直接填入 OAuth code 使用。
2. 将 `FinalsService.login()` 中的会话签发逻辑抽出，供本地登录与飞书回调共用；业务权限仍由服务端本地角色决定。
3. 新增外部身份映射表，把可信的飞书租户和稳定身份 ID 关联到 `users.id`，不依赖姓名。对未知用户显示待授权状态，不自动赋予管理员或评委角色。
4. 为既有业务账号设计显式绑定流程，保留评分、审计和固定名单中的用户 ID；先完成首位正式管理员绑定，再停用初版登录入口或账号。
5. 在最终域名验证授权跳转、回调失败、会话过期、退出、停用、角色隔离和手机飞书内嵌浏览器。具体接口参数按实施时飞书官方文档核对。

应用密钥放服务端环境配置。正式上线前更换这里公开的管理员密码、停用查看评委；若保留本地应急登录，使用独立凭据。

## 5. 部署交付要求

构建命令为 `npm ci`、`npm run build`，运行命令为 `npm start`。NestJS 同时提供构建后的前端与 `/api`，不需要单独运行 Vite 开发服务。

| 配置 | 交接要求 |
| --- | --- |
| `HOST` / `PORT` | 默认 `127.0.0.1:3001`；按反向代理或容器拓扑设置监听地址 |
| `APP_ORIGIN` | 配置实际访问源，核对协议、域名和端口；开发配置不能直接作为生产域名 |
| `COOKIE_SECURE` | HTTPS 环境设置 `true`，回调流程同时核对 SameSite 与 CSRF |
| `DB_PATH` | 指向持久化本地磁盘；目录允许运行用户读写，不放网络共享盘 |
| 进程与代理 | 单个数据库写入服务实例，配置进程守护、TLS、日志与明确的代理信任范围 |
| 备份恢复 | 定期运行 `npm run db:backup`；恢复前停服务，操作见 README，并在目标环境演练 |

数据库启用 WAL，不能只复制主 `.sqlite` 文件作为运行中备份。多实例扩容需先改造数据层。目标服务器安装 `better-sqlite3` 时需验证对应 Node/系统环境可用；本地 Mac 的成功不等同于目标服务器验证。

部署完成后请补交：访问地址、运行环境与启动方式、飞书应用及回调配置位置、首位管理员授权方式、备份路径与恢复步骤、目标环境验收记录。不要把应用密钥填进此文档。

## 6. 参赛材料、视觉完善与正式名单

项目负责人后续协调参赛选手提供材料和确认评委名单；开发同事据此继续完善：

- **参赛材料：**先确定是选手自助提交，还是由管理员收集后录入，再确定文件类型、大小、截止时间、修改权限和可见范围。当前代码没有材料上传接口或文件存储能力，这部分需要单独实现。
- **页面美化：**沿用白色、深蓝、姜黄和原始品牌 logo，优先保证队伍标题、材料入口、分值和提交状态清晰。评分保持滑块＋数字输入，手机不能出现提交栏遮挡内容。
- **正式评委：**按稳定身份逐人配置评委权限，管理员需要评分时单独授予评委角色。正式开赛前核对名单，不能先开赛再用新增账号补名单。
- **队伍更新：**源数据在 `shared/teams.json`，图片在 `client/public/teams/`。数据库采用 `INSERT OR IGNORE` 初始化，直接改 JSON 不会更新已存在的队伍行；已有库需先备份，再用明确迁移更新，保留稳定队伍 ID。

队伍与手册来源、读取版本见 README。程序不会自动拉取飞书文档的后续修改。

后续改动运行 `npm test` 和 `npm run build`，并在目标环境完成以下接收检查：

- 飞书登录的正确租户、首次授权、身份绑定、错误回调和退出流程可用。
- 评委仅能读取与修改本人评分，后台接口不能通过直接访问绕过权限；管理员不能代评。
- 0、0.5、10 分、未评分、改分、均分、并列与 CSV 结果一致。
- 断网草稿、超时重试、双设备冲突、结束评分瞬间提交和服务重启不丢分。
- 实际手机、飞书内嵌浏览器及比赛网络可用；目标环境完成 50 位评委规模验证和一次备份恢复演练。
- 正式库无联调分数，正式评委名单核对完成，初版公开账密已停用或更换。

本轮交接不宣称飞书认证、真机飞书浏览器或生产部署已经通过验收。
